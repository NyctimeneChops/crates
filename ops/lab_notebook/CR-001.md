# CR-001: Project inception, artifact set, and credential exposure incident
Date: 2026-07-21
Status: complete

## What I set out to do

Stand up the project: produce the founding set of planning artifacts, lock the core
product decisions, and get a working demo skeleton (backend, frontend, a small
ingested catalog) far enough to reason about. Partway through, a credential-exposure
incident occurred and remediating it became part of this entry.

### Credential exposure incident

**What leaked.**
- A real `backend/.env` file containing a live **JWT signing key** was committed in
  the initial commit `bac0400` and removed in `87efc7c`.
- The **Neon PostgreSQL connection string** was hardcoded into six utility scripts
  rather than read from the environment. It appears across commits `f1fa445`,
  `0290130`, `2503208`, and `0bc60fb`. (Of those six scripts, four `check_*` scripts
  remained in the working tree at remediation time and were refactored; two `fix_*`
  scripts had already been deleted in `0290130`.)

**Exposure — two distinct windows (do not conflate them).**

- **Window A — present in local git history (private, never publicly readable).**
  The secret entered the repository in `bac0400` (initial commit) at
  **2026-05-24 16:36:12 −07:00 (23:36:12 UTC)** and was removed from the working tree
  in `87efc7c` at **2026-05-24 16:37:31 −07:00 (23:37:31 UTC)** — about 79 seconds
  later. The value nonetheless persisted in local git *history* (in the `bac0400`
  blob) until the history was purged during this remediation. Throughout Window A the
  history was local and private; it was never publicly readable.

- **Window B — publicly readable on GitHub (the window that actually matters).**
  Start: **2026-07-21 19:38:58 UTC**, the push timestamp reported by the GitGuardian
  alert on commit `87efc7c` (the removal commit). End: **approximately
  19:55–20:00 UTC**, when the Neon role password and the JWT signing key were both
  rotated. **Total public exposure: roughly 15 to 20 minutes.** Rotation times are
  estimated to within about 5 minutes; they were not logged precisely at the time.

**How it was detected.** Detection was independent and near-immediate: Neon's own
scanner and GitGuardian both alerted on the same push, with GitGuardian raising two
separate findings.

**Severity — low.** Public exposure was **minutes, not days**, and no evidence of
unauthorized access was found. The Window A / Window B distinction is the reason this
stayed low-severity despite the secrets sitting in local history much longer: that
history was private until the push, and the publicly-readable window was short and
closed by prompt rotation.

**What was rotated.**
- The **JWT signing key** was rotated.
- The **Neon role password** was rotated.

**What turned out NOT to be exposed.**
- **SoundCloud credentials** were never committed. No SoundCloud rotation was needed.

### Root cause

Two independent mistakes:
1. Throwaway utility scripts **hardcoded the database connection string** inline
   instead of reading it from the environment.
2. A **real `.env`** file was committed in the initial commit.

## What I learned

- Convenience scripts are the soft spot. The application code read config from the
  environment correctly; the leak came entirely from one-off scripts written in a
  hurry. Those need the same discipline as production code.
- Detection worked (two independent systems caught it), but detection is not
  prevention. The fix has to make the leak hard to create in the first place.
- **The local pre-commit hook is the primary secret control for the private repo, not
  a redundant backstop.** Push protection is unavailable on a private personal-account
  repository (see above), so the Step-1.8 pre-commit hook is the *only* secret
  protection covering `Crates-internal`. On the public repo the hook is a second layer
  behind GitHub push protection; on the private repo it is the first and only layer.
  That asymmetry is worth remembering before trusting the private repo to catch a
  mistake the hook doesn't.

### Remediation applied

- **Shared `db.py` helper** (`backend/db/config.py`, re-exported from `db`): a single
  `get_database_url()` that reads `DATABASE_URL` from the environment and raises if it
  is missing. Scripts import this instead of pasting a URL.
- **`backend/scratch/`** directory for throwaway scripts, gitignored except its
  `README.md`, which documents the "never hardcode a connection string" rule and ships
  a copy-paste template that reads from the environment.
- **Pre-commit hook** (`.git/hooks/pre-commit`) that scans staged additions for
  connection strings, private keys, long hex strings, bearer tokens, and
  secret-shaped assignments, and blocks committing any real `.env` file.
- **Git history purged.** The old `.git` (which still contained the leaked values in
  history) was backed up outside the project and replaced with a fresh history, since
  the remote repositories were deleted and recreated empty.
- **Push protection (differs per repository).**
  - **Crates (public):** not active yet at the time of writing. GitHub secret scanning
    and push protection are free and enabled by default on *public* repositories, so
    this becomes active automatically once the repository is made public. Action item:
    verify the toggle under Settings > Code security after flipping it public.
  - **Crates-internal (private, personal account):** push protection is **not
    available**. GitHub secret scanning / push protection for *private* repositories
    require GitHub Secret Protection, a paid product on Team or Enterprise plans, and
    it is not offered on individual plans at any tier.

## What's next

Open items, none of which currently have a designed solution:

- **Session upload friction** has no designed mitigation yet. Getting session files
  out of a producer's DAW and into the product is an unsolved UX problem.
- **The discovery-correlation experiment is blocked** until there is a real user base
  to draw behavioural data from. With one user (the author), there is nothing to
  correlate.
- **The vendor registry has no contribution mechanism** — there is no way for outside
  parties to add or maintain entries.

Immediate follow-ups:

- **Verify push protection is active on Crates** under Settings > Code security after
  making the repository public.
- **Consider adding gitleaks to the pre-commit hook** for stronger local coverage than
  regex matching alone — this matters most for `Crates-internal`, where the hook is the
  only control.
